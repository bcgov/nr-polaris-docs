# Build Environment Setup

## Overview

The `env.sh` script initializes your build environment for CI/CD pipelines by loading service configuration, authenticating with Knox Vault, and sourcing build-specific environment variables and credentials from your catalog-info.yaml directory.

## Usage

```bash
source env.sh [build|local] [PATH] [--skip-vault]
```

### Arguments

| Argument | Description | Default |
|----------|-------------|---------|
| `build\|local` | Development environment mode | `build` |
| `PATH` | Directory containing `catalog-info.yaml` | Current directory (`.`) |
| `--skip-vault` | Skip Vault authentication (for CI/CD or offline builds) | False |

### Modes

**`build`** - Build Mode (default)
- Loads configuration from `.env-build.sh` in your PATH directory
- Used for CI/CD pipelines and standard build operations
- Includes full build credentials

**`local`** - Local Development Mode
- See [LOCAL.md](LOCAL.md) for local development setup and runtime documentation

## Examples

```bash
# Load from current directory, build mode (default)
source env.sh

# Load from a specific directory in build mode
source env.sh build ./backend

# Load from current directory with Vault authentication skipped
source env.sh build --skip-vault
```

For local development examples, see [LOCAL.md](LOCAL.md).

## How It Works

The `env.sh` script performs the following steps:

1. **Validates catalog-info.yaml** - Confirms that the specified PATH contains a valid Backstage Component manifest
2. **Authenticates with Knox Vault** - Retrieves authentication tokens (unless `--skip-vault` is specified)
3. **Sources configuration files** - Loads `.env-build.sh`

## Configuration Files

### .env-build.sh (Auto-Generated)

This file is automatically generated and handles:
- Service identification (`PROJECT_NAME`, `SERVICE_NAME`)
- Build configuration (e.g., `POM_ROOT`, `MAVEN_ARGS`)
- **Read-only artifact repository credentials** from Vault

Do not edit this file directly.

## Environment Variables Set

The script configures the following environment variables:

| Variable | Description | When Set |
|----------|-------------|----------|
| `VAULT_ADDR` | Knox Vault server address | Always |
| `VAULT_TOKEN` | Vault authentication token | When `--skip-vault` is not used |
| Build secrets | Variables from `.env-build.sh` | Always |

## Build Secrets Configuration

The environment setup uses different credential sets depending on where the build runs:

### `toolsBuildSecrets` - CI/CD Pipeline Credentials

- Default: `ARTIFACTORY_USERNAME,ARTIFACTORY_PASSWORD`
- Used in CI/CD pipelines (GitHub Actions, automated tools)
- Contains full write access for artifact publishing
- Configured in `catalog-info.yaml` under `metadata.annotations.playbook.io.nrs.gov.bc.ca/toolsBuildSecrets`

### `toolsLocalBuildSecrets` - Local Development Build Credentials

- Default: Same as `toolsBuildSecrets` but should be restricted to read-only access
- Used when running `env.sh build` on your development machine
- **Critical:** Should only contain **read-only credentials** for security
- Used for downloading/reading artifacts during local builds (e.g., `mvnw clean package`)
- Should NOT contain write/publish access to prevent accidental publication from your workstation
- Configured in `catalog-info.yaml` under `metadata.annotations.playbook.io.nrs.gov.bc.ca/toolsLocalBuildSecrets`

### Security Best Practice

Keep your local build credentials separate and read-only to prevent accidentally publishing artifacts or modifying production repositories from your development machine.

## Updating Build Secrets

To change which credentials are loaded during CI/CD builds:

1. Edit your root `catalog-info.yaml`
2. Update the service annotations:
   ```yaml
   metadata:
     annotations:
       playbook.io.nrs.gov.bc.ca/toolsBuildSecrets: "ARTIFACTORY_USERNAME,ARTIFACTORY_PASSWORD"
       playbook.io.nrs.gov.bc.ca/toolsLocalBuildSecrets: "READ_ONLY_ARTIFACTORY_USERNAME,READ_ONLY_ARTIFACTORY_PASSWORD"
   ```
3. Regenerate environment files using the appropriate playbook generator (pd-java-playbook, pd-oci-playbook, etc.)
4. Re-source `env.sh` in your shell
