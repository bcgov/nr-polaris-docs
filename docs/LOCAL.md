# Local Development

## Overview

The `env.sh local` script initializes your local development environment by loading configuration and authentication credentials. It validates your service configuration, authenticates with Knox Vault (unless disabled), and sources local development environment variables from your catalog-info.yaml directory.

## Usage

```bash
source env.sh [build|local] [PATH] [--skip-vault]
```

### Arguments

| Argument | Description | Default |
|----------|-------------|----------|
| `build\|local` | Development environment mode | `build` |
| `PATH` | Directory containing `catalog-info.yaml` | Current directory (`.`) |
| `--skip-vault` | Skip Vault authentication (for CI/CD or offline builds) | False |

### Modes

**`build`** - Build Mode (default)
- See [BUILD.md](BUILD.md) for build setup and credentials

**`local`** - Local Development Mode
- Loads configuration from both `.env-build.sh` and `.env-local.sh`
- Used for running builds on your development machine
- Applies read-only credential restrictions for security

## Examples

```bash
# Load from current directory, local development mode
source env.sh local

# Load from a specific service directory
source env.sh local /path/to/service

# Skip Vault authentication (for offline development)
source env.sh local --skip-vault
```

## How Local Setup Works

When you run `source env.sh local`, the script:

1. **Validates catalog-info.yaml** - Confirms your service exists and is properly configured as a Backstage Component
2. **Authenticates with Knox Vault** - Retrieves authentication tokens (unless `--skip-vault` is specified)
3. **Sources .env-build.sh** - Loads auto-generated service identification and Maven configuration
4. **Sources .env-local.sh** - Loads your local development-specific environment variables and settings

## Configuration Files

### .env-build.sh (Auto-Generated)

This file is automatically generated and handles:
- Service identification (`PROJECT_NAME`, `SERVICE_NAME`)
- Build configuration (e.g., `POM_ROOT`, `MAVEN_ARGS`)
- **Read-only artifact repository credentials** from Vault

Do not edit this file directly.

### .env-local.sh (Your Custom Settings)

This file is where you add application-specific settings for your local development environment. It is not generated automatically.

⚠️ **Security Warning:** Never commit secrets or credentials directly to `.env-local.sh`. Instead, store secrets in Vault (preferably in the `tools` namespace) and fetch them dynamically in your script, as shown in the example below.

Create `.env-local.sh` in your service directory with your custom settings:

```bash
#!/bin/bash

# .env-local.sh - Local development environment settings
# (.env-build.sh is already sourced with auto-generated configuration)

# Application configuration
export APP_ENV=development
export LOG_LEVEL=debug

# Database connection (if your app needs a local database)
export DATABASE_URL=jdbc:postgresql://localhost:5432/myapp_dev

# Cache settings for development
export CACHE_ENABLED=false

# Any other development-specific settings
export DEV_FEATURE_FLAG=true

# Example: Fetch additional secrets from Vault if needed
# (Only fetch if Vault authentication is available)
if [[ "$SKIP_VAULT" != "true" ]]; then
  # Fetch a custom secret field from Vault
  export MY_CUSTOM_API_KEY=$(vault kv get -field=api_key "apps/tools/${PROJECT_NAME}/${SERVICE_NAME}")
fi
```

## Environment Variables

When you source `env.sh local`, the following variables are available:

| Variable | Source | Purpose |
|----------|--------|---------|
| `VAULT_ADDR` | env.sh | Knox Vault server address |
| `VAULT_TOKEN` | Vault auth | Authentication token (if not skipped) |
| `PROJECT_NAME` | .env-build.sh | Service project identifier |
| `SERVICE_NAME` | .env-build.sh | Service name |
| Build credentials | .env-build.sh | Read-only artifact repository access |
| Custom variables | .env-local.sh | Your application-specific settings |

## Running Your Service

After sourcing `env.sh local`, refer to your service repository's documentation for the commands to run your service. The specific commands depend on your service type and implementation.
